# Architecture context for RSC bundle optimization

## Purpose

This work has two goals:

1. Reduce the bundle cost of `@spectrum-charts/react-spectrum-charts-s2` now.
2. Make each optimization leave behind boundaries that remain useful if RSC is
   later refactored, rebuilt on a lean Vega runtime, or rebuilt on Direct D3.

Bundle work must not pre-decide the engine evaluation. It should improve the
current product while making the eventual implementation easier to replace.

## Mission statement carried into this packet

RSC has two equal top-level purposes:

1. An authoritative set of Spectrum visualization tokens, behaviors, and
   guidelines that can guide any implementation, including bespoke charts
   generated by engineers or AI tools.
2. A curated library of declarative chart components that applies those rules
   by default for common, well-understood chart types.

The first purpose matters because RSC can no longer be assumed to be the literal
implementation behind every Adobe visualization. The durable asset is the
design and behavior system that keeps independently built visualizations
consistent.

The second purpose remains equally important because guidelines alone do not
prevent every team from rebuilding the same charts or producing subtly
different behavior. RSC should remain the high-quality default implementation
for common chart families.

The mission also makes optimized, continuously measured bundles a hard
deployment requirement. Chart capabilities must eventually be usable outside
React, support SVG and Canvas, support server rendering, and expose consistent
interaction and accessibility behavior.

The complete implementation requirements relevant to this work are:

- SVG and Canvas rendering.
- Equivalent keyboard navigation in both renderers.
- Optional browser-style event bindings for every meaningful rendered element.
- Equivalent synthetic event dispatch for Canvas.
- Built-in opacity and drawing animation.
- Tightly optimized and continuously measured bundle size.
- Per-mark and per-capability bundle reporting.
- Non-React use of non-React features.
- Server-side rendering.
- Human and agent-readable documentation for tokens, guidelines, behaviors,
  and components.

Implementation technology is a means rather than a mission goal. Vega, lean
Vega, and Direct D3 must be judged by how well they satisfy those requirements.
The existing Vega implementation is being reconsidered because small features
often cross the React adapter and spec-builder layers, creating high authoring
cost and unreliable changes. That does not mean Vega is always the wrong
primitive; it means the current architecture and runtime floor require
evidence-based comparison.

The implication for this project is that bundle optimization is not only a
build-tool exercise. The package structure should increasingly separate:

```text
Public React API and chart definitions
                  |
       chart-family capability
                  |
      shared host/lifecycle contract
                  |
       compiler/runtime adapter
        /          |          \
 current Vega   lean Vega   Direct D3
```

The current work should move toward that shape without attempting to finish the
entire rebuild architecture inside a bundle project.

## Current RSC architecture

The current S2 runtime follows this path:

```text
React children
  -> childrenAdapter.ts
  -> ChartOptions
  -> chartSpecBuilder.ts
  -> Vega Spec
  -> VegaChart.tsx
  -> vega-embed
  -> Vega View
```

Important current coupling:

- `src/utils/utils.ts` imports all chart and child components to build
  `displayName` allowlists.
- `src/rscToSbAdapter/childrenAdapter.ts` imports all components and all adapter
  functions.
- `vega-spec-builder-s2/src/chartSpecBuilder.ts` imports all mark compiler
  functions.
- `src/hooks/useSpec.tsx` always calls the monolithic `buildSpec`.
- `src/VegaChart.tsx` directly owns Vega rendering through `vega-embed`.
- The package root re-exports the complete spec-builder package.

That is why a fixture importing one mark is currently almost the same size as a
fixture importing every mark.

## Prototype measured baseline

The prototype profiling workspace on the `bundle` branch reports approximately:

| Scenario | Gzip |
|---|---:|
| Cold consumer, one mark | 662.6 KB |
| Cold consumer, every mark | 663.9 KB |
| React/Spectrum already shared | 604.6 KB |
| Vega plus Vega-Lite in isolation | 196.1 KB |

The one-mark/every-mark difference is only about 1.3 KB. This is useful
directional evidence that most current cost is a shared runtime floor, not
individually imported chart code. Ticket 00 must validate and productionize the
harness before these values become the official baseline.

This means the priority order should be:

1. Measure consistently.
2. Remove unnecessary runtime dependencies.
3. Produce real ESM.
4. Remove eager dispatch edges.
5. Publish complete chart-family boundaries.

## Three possible long-term outcomes

### Existing RSC refactor

RSC keeps its existing public API and Vega behavior but replaces the expensive
adapter and compiler organization.

This is the lowest-migration-cost path. It retains the mature React API,
Spectrum theming, stories, localization, existing chart breadth, and solved
Vega behavior. Its central risk is retaining the same extension cost and a
large runtime/package floor if the refactor does not create real capability and
lifecycle boundaries.

Bundle work helps by:

- Moving from UMD to ESM.
- Removing `vega-embed`.
- Separating chart-family adapters and compilers.
- Establishing a smaller host/runtime boundary.
- Creating conformance and bundle fixtures for incremental migration.

### Ground-up lean Vega

A new compiler uses selected RSC Vega mechanisms without copying the existing
builder architecture.

The research direction is not to wrap `vega-spec-builder-s2`. Existing RSC
should be treated as a behavior and Vega-mechanism corpus: extract proven marks,
transforms, scales, signals, event streams, invariants, and runtime behavior,
then design a smaller compiler and direct `vega.View` adapter around the mission
requirements.

The measured lean-Vega experimental browser entry was approximately 262.6 KB
gzip. Its main structural disadvantage is the Vega runtime floor. Its advantage
is that Vega already supplies scales, transforms, marks, signals, SVG, Canvas,
formatting, and mature rendering behavior.

Bundle work helps by:

- Establishing direct `vega.View` ownership now.
- Removing the Vega-Lite and `vega-embed` layer.
- Separating host lifecycle from compiler selection.
- Defining per-family loading boundaries.
- Keeping compiled Vega programs internal and opaque.

### Direct D3 rewrite

A compiler produces an owned retained scene rendered by generic SVG and Canvas
surfaces.

The experimental Direct D3 runtime used a JSON-safe
Definition -> Layout -> Scene -> Surface pipeline with shared SVG and Canvas
visitors. The measured prototype was approximately 32.8 KB gzip.

Its advantage is bundle size, direct control, and localized feature ownership.
Its cost is that RSC must own more layout, interaction, picking, animation,
accessibility, and lifecycle infrastructure.

Bundle work helps by:

- Keeping the public API independent from Vega types.
- Establishing per-family modules.
- Separating runtime-only callbacks from serializable chart configuration.
- Establishing lifecycle, bundle, and conformance tests that a D3 runtime can
  later satisfy.

The direct Vega implementation itself would not transfer to D3, but the host
boundary and tests around it would.

## Long-term architecture target

The current leading architectural direction is:

- A stable product-facing API.
- JSON-safe chart definitions.
- Runtime callbacks and DOM objects kept outside serialized definitions.
- Pre-bound chart-family modules rather than a mandatory central registry.
- A shared host controller for mount, update, resize, destroy, SSR, and
  attachment.
- A capability-checked compiler/runtime seam.
- Opaque engine programs rather than a universal public rendering spec.
- Optional dynamic registries only where input arrives with an unknown chart
  family.

A conceptual future family module could expose:

```ts
barChart.define(input);
barChart.mount(container, definition, runtimeBindings);
barChart.renderToSvg(definition);
```

The bundle tickets do not need to create that public API. They should avoid
making it harder to reach.

Before an architecture is considered migration-ready, it must prove:

1. A production Bar consumer can migrate without silent behavior regressions.
2. Line uses the same contracts rather than creating a second architecture.
3. A structurally different family can use the same host and packaging model.
4. Bar consumers do not pay for unrelated chart families.
5. SVG and Canvas expose equivalent semantic interaction targets.
6. Mount, update, resize, destroy, remount, SSR, and attachment are
   deterministic.
7. Bundle, runtime, and memory budgets are continuously measured.
8. Migration can be introduced gradually and rolled back.

## `UNSAFE_vegaSpec` compatibility debt

The current public API exposes:

```ts
UNSAFE_vegaSpec?: Spec;
```

This is an explicit leak of the current engine program. The `UNSAFE_` prefix
discourages reliance on it but does not make it private.

Its effect on each outcome is different:

| Outcome | Compatibility |
|---|---|
| Existing RSC refactor | Can remain supported |
| Lean Vega | Can probably remain supported behind the Vega compiler/runtime |
| Direct D3 | Cannot be implemented natively because no Vega spec exists |

The bundle work should not remove the prop accidentally. Before a Direct D3
migration, RSC must explicitly choose one of:

1. Deprecate and eventually remove the escape hatch.
2. Keep a separately loaded Vega compatibility runtime for unsafe specs.
3. Keep legacy RSC available for charts using the escape hatch.

Do not attempt to translate arbitrary Vega specs into D3 scenes. That would
create a second chart engine project and an unreliable compatibility promise.

## Architectural rules for these tickets

### Prefer explicit composition over import-time registration

Do not introduce a mandatory global registry populated by side effects. It is
fragile under tree-shaking, duplicate package installations, SSR, and test
isolation.

Static consumers should import a pre-bound family module. A dynamic registry is
appropriate only where input arrives with an unknown chart type, such as an AI
catalog.

### A subpath must be a complete usable capability

This is not sufficient:

```ts
import {Bar} from '@spectrum-charts/react-spectrum-charts-s2/Bar';
```

`Bar` currently renders `null`; the costly work remains in `Chart`, the
sanitizers, adapters, compiler, and runtime.

A meaningful entry looks more like:

```ts
import {
  Chart,
  Bar,
  Axis,
  Legend
} from '@spectrum-charts/react-spectrum-charts-s2/bar';
```

That entry must bind a Bar-capable chart host to only the adapters and compiler
capabilities Bar requires.

### Keep engine programs opaque

Do not create a universal public rendering specification. Public definitions,
runtime bindings, lifecycle, semantic targets, and accessibility contracts
should be engine-neutral. Vega specs and future D3 retained scenes should remain
private compiler outputs.

### Preserve the compatibility barrel

The root package should continue to support existing imports. It may compose
every capability and therefore remain larger. Optimization comes from adding
better entry points, not silently changing existing behavior.

### Measure incremental cost, not only artifact size

Each change must distinguish:

- Cold-consumer gzip.
- Shared-host gzip.
- Package tarball/raw duplication.
- Shared runtime floor.
- Incremental chart-family cost.

For example, removing duplicated `index.js` and `ai-catalog.js` code can reduce
package output substantially without reducing an application that imports only
one of those entries.

## Bundle estimate caveats

All ticket estimates are planning ranges, not acceptance thresholds. They must
be replaced by measurements from `packages/bundle-profiling`.

The direct Vega ticket has the largest expected immediate reduction because
`vega-embed` imports Vega-Lite and supporting packages. Removing the separate
Vega-Lite peer declaration afterward improves installation and contract clarity
but should not claim those runtime bytes a second time.

Per-family savings are uncertain until both eager dispatcher layers are removed.
The current 1.3 KB one-mark/everything difference is evidence that subpath
exports alone will not be useful.

## Optionality has a real cost

The following work goes beyond the strict minimum required to reduce today's
bundle:

- Typed component capability metadata.
- Keeping compiler functions outside serialized `ChartOptions`.
- Separating compiler selection from the shared compiler core.
- Building complete chart-family entries instead of component aliases.

A smaller short-term change could use local lookup tables designed only around
the existing Vega implementation. The proposed structure costs additional
design and test effort because it preserves options for lean Vega and Direct
D3.

That is an intentional tradeoff, not a free side effect of tree-shaking. The
cost is considered reasonable because:

- Component descriptors are small and private.
- Compiler injection stays internal.
- Both changes directly remove current eager imports.
- They avoid introducing another mandatory global registry.
- They do not require committing to a universal engine abstraction.

The long-term architecture owner should still confirm this investment before
Tickets 06-10 begin.
